## Context

当前笔记模块建立在三个前提上：一是以 overlay 形式覆盖主工作区，二是以文件系统中的 Markdown 文件作为唯一数据源，三是以“文件树 + 多 Tab 编辑器”作为主要交互模型。这个组合已经能完成基础读写，但实际体验存在几个结构性问题：

- 交互重心过度偏向文件管理，导致用户在“找一条笔记并继续写”时需要频繁在树结构与 Tab 之间来回切换。
- 多 Tab 模型提高了状态复杂度，但并没有带来足够的收益，反而让当前文档、脏状态、重命名后的路径同步变得更脆弱。
- 自动保存已经具备写盘能力，但没有把保存状态反馈给 UI，用户无法直观看到“正在写入”还是“已经保存”。
- 工作台级导航能力缺失，最近访问、收藏、恢复上次上下文等都需要依赖用户重新在树中定位。

本次变更的约束已经明确：

- 保留笔记作为 overlay 的存在形式，不改成常驻主面板。
- 笔记是全局笔记本，而不是跟当前 workspace 强绑定的项目笔记。
- 第一阶段只做轻量高质基础版，不引入双链、标签、模板、知识图谱等扩展能力。
- 保留强文件夹层级入口。
- 改为单文档编辑流，不保留多标签页。

## Goals / Non-Goals

**Goals:**

- 在不改变 overlay 总体入口方式的前提下，将笔记模块重构为更完整的工作台式交互。
- 保留文件系统作为事实来源，继续直接编辑 `.md` 文件。
- 将状态模型从多 Tab 收敛为单文档，降低实现与交互复杂度。
- 增加最近、收藏、全部视图与上次上下文恢复，减少重复定位。
- 让自动保存状态对用户可见。

**Non-Goals:**

- 不将笔记模块改造成主工作区常驻 panel。
- 不引入数据库、远程同步服务或新的第三方富功能笔记依赖。
- 不实现双链、标签、模板、全文索引、高级知识管理能力。
- 不为旧的多 Tab 笔记行为保留兼容模式。

## Decisions

### 1. 保留 overlay 外形，但将内部重构为更紧凑的三段式工作台

笔记仍然保持与浏览器、Git Diff 一致的 overlay 入口，这样不会打破现有工作区的整体交互语言。但 overlay 内部不再是简单的“左树右编辑器”，而是重构为：

```text
icon 视图栏 | 合并导航树 | 编辑区
```

选择这个结构的原因：

- 用户已经明确要求保留 overlay，所以不再考虑升格为主 panel。
- 最左侧的视图切换仍有价值，但应退化为纯 icon rail，只承担模式切换，不再占用文本布局空间。
- 用户已经明确要求文件夹树与笔记列表合并成单一树结构，因此导航区需要重新回到“树即定位、树即浏览”的统一入口。
- 编辑区仍然是主任务区域，因此左侧导航必须进一步压缩，让横向空间优先留给正文。

备选方案：

- 继续沿用“树 + Tab”结构：实现成本较低，但无法根治当前体验问题。
- 做成四栏“视图栏 + 文件夹树 + 笔记列表 + 编辑区”：浏览职责更明确，但横向占用过大，已经被本轮实现反馈否定。

收敛补充：

- 视图栏应收敛为仅保留 icon 的导航带，不再展示文字标签。
- 文件夹树与笔记列表应合并为一个导航树，避免左侧出现两个并列内容区。
- 若布局空间不足，优先压缩导航区，而不是压缩编辑区。

### 2. 用单文档状态模型替代多 Tab

工作台内部以单个 `currentNotePath` 作为当前文档来源，不再维护打开中的 Tab 集合。围绕它再维护：

- `activeView`: `recent | favorites | all`
- `selectedFolderPath`
- `searchQuery`
- `currentNotePath`
- `workspaceContext`

选择单文档模型的原因：

- 这次目标是“轻量高质基础版”，多 Tab 不符合这个产品气质。
- 当前实现里 tab content、autosave queue、重命名后的路径更新之间已经存在一致性风险。
- 单文档切换可以自然与“切换前 flush”结合，状态行为更容易预测。

备选方案：

- 保留多 Tab：更接近 IDE，但会放大状态同步复杂度。
- 混合模式（默认单文档，可临时 pin）：收益有限，第一阶段没有必要。

### 3. 最近、收藏与上下文恢复采用独立的轻量持久化状态

笔记正文仍然只保存在 Markdown 文件中；最近访问、收藏、当前视图、上次文件夹与上次文档这类工作台导航状态，不写入笔记正文，也不生成额外 sidecar 文件，而是以本地轻量持久化状态保存。

推荐实现形态：

- 使用独立的前端持久化结构保存工作台状态
- 内容包括收藏列表、最近访问时间、上次上下文
- 文件系统仍然是笔记内容的唯一事实来源

选择这个方案的原因：

- 这些信息属于 UI/工作台状态，不属于笔记正文。
- 不修改笔记目录结构可以避免污染用户文件。
- 第一阶段无需引入数据库或索引层。

备选方案：

- 把状态写入独立 metadata 文件：可移植性更强，但会引入新的文件管理复杂度。
- 只放在内存里：实现简单，但无法恢复上次上下文。

### 4. `全部` 视图保持文件夹驱动，`最近` / `收藏` 作为全局快捷入口

在 `全部` 视图下，导航树以文件夹层级为主；在 `最近` 和 `收藏` 视图下，同一导航树切换为对应结果集，而不是再额外占用一列笔记列表。

选择这个方案的原因：

- 它保留了“强文件夹层级入口”这一用户要求。
- 也允许用户跳过层级导航，快速进入高频笔记。
- 通过在同一棵导航树中切换数据视图，可以避免双列导航造成的空间浪费。

备选方案：

- 让 `最近` / `收藏` 继续受当前文件夹过滤：会增加理解成本，且削弱全局快捷入口的价值。
- 只提供树驱动，不做视图栏：无法达到“轻量高质基础版”的导航体验目标。

### 5. 文件夹树交互与文件系统模块保持一致

笔记工作台中的导航树不再使用独立的交互语法，而应尽量对齐文件系统模块中的文件树交互习惯，包括展开/收起方式、选中反馈、层级缩进、悬停动作显隐和整体视觉密度。

选择这个方案的原因：

- 用户已经明确要求笔记侧边栏回到文件系统模块文件树那套交互。
- 文件树属于高频肌肉记忆区，对齐现有文件系统模块可以降低重新学习成本。
- 这能避免笔记模块形成另一套近似但不同的树交互规则。
- 合并导航树后，统一复用文件树式交互比继续维护“树 + 列表”两套语法更合理。

备选方案：

- 保留独立的笔记树交互：可以更自由定制，但会继续增加认知切换成本。
- 完全复用文件系统组件：一致性最高，但当前笔记导航树仍有视图切换和笔记动作约束，短期更适合先对齐结构和交互语法，而非强行共用组件。

### 6. 自动保存从“仅写盘”升级为“写盘 + 状态机反馈”

现有 autosave 机制保留 debounce、串行写入与 flush 逻辑，但需要新增可消费的保存状态。推荐状态至少包括：

- `editing`: 当前文档有未保存修改
- `saving`: 正在写盘
- `saved`: 最近一次保存成功且当前无未保存修改

NotePanel 只消费这个状态并渲染文案，不直接参与写入调度。

选择这个方案的原因：

- 可以尽量复用现有 autosave 能力，不重写写入核心。
- 状态归属仍在 autosave 层，UI 只负责展示，职责清晰。

备选方案：

- 在 NotePanel 本地拼装状态：实现快，但容易和真实写入进度脱节。
- 每次保存后仅 toast 提示：缺少持续可见的状态反馈。

## Risks / Trade-offs

- [把视图切换、目录定位和结果浏览都合并进导航树后，树可能变得过重] → 通过 icon 视图栏负责模式切换，导航树只负责在当前模式下展示一致的数据结构，避免再拆分第二列结果区。
- [单文档替代多 Tab 可能让少量重度用户不适应] → 本次 change 明确以轻量高质基础版为目标，不保留兼容模式，避免产品方向摇摆。
- [最近/收藏状态与真实文件系统可能出现漂移] → 每次加载工作台时做存在性校验，失效项自动跳过。
- [autosave 状态反馈与真实写盘过程不一致] → 状态只由 autosave 模块统一驱动，避免 UI 本地推断。
- [overlay 内信息密度提升后容易显得拥挤] → 通过固定区域职责、压缩左侧导航占比并让编辑区保持主导来控制密度，不继续叠加复杂功能。
- [笔记树与文件系统树的实现分叉会导致维护成本上升] → 交互规则先向文件系统树对齐，后续若稳定再考虑进一步抽象复用。

## Migration Plan

这次变更不涉及笔记内容格式迁移，已有 Markdown 文件保持原样继续使用。

实施步骤上：

1. 先重构笔记工作台状态模型与布局骨架。
2. 再接入最近、收藏、上下文恢复等导航状态。
3. 最后将 autosave 状态透出到 UI，并清理多 Tab 遗留逻辑。
4. 在工作台基本可用后，再将视图栏收敛为 icon rail，并把文件夹树与笔记列表合并为单一导航树。
5. 最后继续对齐文件系统模块文件树的交互与视觉密度。

回滚策略上，若需要回退，只需恢复旧的 NotePanel 与 autosave 展示逻辑；笔记文件本身不会受到结构性影响。
