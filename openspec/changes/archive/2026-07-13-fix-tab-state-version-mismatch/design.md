## Context

Tab 状态通过 `TerminalPanel` 构建快照，经 preload IPC 交给主进程写入 `<userData>/tab-state.json`；启动时 `loadTabState` 读取并校验后，再由 `TerminalPanel` 重建 workspace、terminal session 和活跃状态。

加入 terminal transcript 后，持久化 schema 新增了 `transcriptId`，读取端的当前版本被提升为 `2`，但 `TerminalPanel` 的快照构建仍硬编码为 `version: 1`。文件写入本身成功，加载时却必然因为版本不匹配而返回 `null`。当前项目没有 Tab 持久化的自动化测试，因此这种跨模块常量漂移未被及时发现。

## Goals / Non-Goals

**Goals:**

- 让新写入的 Tab 状态始终携带读取端认可的当前 schema 版本。
- 让版本号只有一个代码来源，避免保存与读取逻辑再次漂移。
- 自动化验证当前版本可恢复、非当前版本被拒绝。
- 保持现有 IPC、文件路径与 session 恢复流程不变。

**Non-Goals:**

- 不迁移或兼容读取旧 schema 版本。
- 不改变 Tab 状态字段、transcript 生命周期或 PTY 恢复语义。
- 不恢复已经被默认 workspace 覆盖的历史状态文件。

## Decisions

### 决策 1：由持久化工具模块统一拥有当前 schema 版本

在 `tab-persistence` 模块导出唯一的当前版本定义，并提供构建当前版本快照的纯函数。`TerminalPanel` 只传入业务状态字段，不再自行填写数字版本；加载校验使用同一版本定义。

选择这一方案是因为错误来自同一个协议版本在两个模块中分别硬编码。仅把 `TerminalPanel` 中的 `1` 改为 `2` 虽能修复当下问题，但下一次 schema 升级仍可能重现漂移。把版本注入收敛到持久化边界，可以在类型与测试层面固定这一不变量。

替代方案：继续在保存端和读取端各自维护常量。改动更小，但无法消除本次回归的结构性原因，因此不采用。

### 决策 2：严格拒绝非当前版本，不增加迁移分支

`loadTabState` 继续只接受当前 schema 版本，版本不匹配时返回 `null` 并走现有默认 workspace 行为。本次不为版本 `1` 增加补全 `transcriptId`、条件接受或原地升级逻辑。

该选择遵循项目“不主动编写兼容性代码”的约束，并让修复聚焦于保证后续写入正确。其代价是修复版本首次启动时，之前由故障版本写下的 `version: 1` 文件仍不会恢复；用户在修复版本中重新建立的 Tab 状态会以当前版本写入，之后启动可正常恢复。

替代方案：兼容读取带 `transcriptId` 的版本 `1` 数据并迁移到版本 `2`。这能减少一次性状态丢失，但属于明确的兼容/迁移逻辑，不纳入本变更。

### 决策 3：在工具模块边界测试版本契约

新增针对 `tab-persistence` 的 Node 测试，至少覆盖：快照构建使用当前版本、当前版本完整状态可加载、版本不匹配状态被拒绝。测试使用 stub 的 `window.tabStateApi` 隔离 Electron 环境，不启动完整应用。

这样可以直接覆盖本次失效条件，且与项目现有基于 `node:test` 加载 TypeScript 工具模块的测试方式一致。完整 Electron 退出/重启仍作为手工验证项，因为当前项目没有端到端测试基础设施。

## Risks / Trade-offs

- [修复版本首次启动仍拒绝既有 `version: 1` 文件] → 明确作为无兼容策略的已知代价；验收从修复版本重新保存当前版本状态后开始验证重启恢复。
- [纯工具测试未覆盖 Electron 关闭时序] → 保留一次实际创建多个 Tab、退出并重启的手工验证，确认同步写文件和 PTY 重建链路仍正常。
- [未来新增 schema 字段但忘记升级版本] → 版本号仍需开发者主动更新；单一来源只消除读写数字不一致，后续 schema 评审仍需检查版本语义。
