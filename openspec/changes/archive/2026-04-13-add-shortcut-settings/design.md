## Context

当前应用已经有部分硬编码快捷键和局部显隐状态：

- `App.tsx` 直接监听键盘事件，预留了面板切换快捷键
- 文件树显隐状态由 `App.tsx` 维护，并通过 `SplitLayout` 控制左栏收起/展开
- terminal 侧边 tab 栏显隐、workspace 新建等行为由 `TerminalPanel.tsx` 内部管理
- 主题模式已经采用本地持久化方式保存，说明当前应用已经接受“渲染进程内配置 + localStorage 持久化”的模式

这次变更同时覆盖应用根组件、terminal 面板和新增设置 UI，属于跨模块能力建设。用户已经明确本次只实现最小可用的快捷键设置与设置面板，不实现 which-key 提示面板，也不要求兼容性分支。

## Goals / Non-Goals

**Goals:**
- 提供一个可被 `Command + ,` 打开的应用内设置面板
- 提供一套统一的快捷键定义、读取、保存与运行时派发机制
- 支持配置 3 个动作的快捷键：文件树显隐、terminal tab 侧边栏显隐、新增 workspace
- 让设置保存后的快捷键立即生效，并在重启应用后保持
- 为未来继续扩展更多快捷键动作和 which-key 提示系统预留稳定的动作标识

**Non-Goals:**
- 不实现 which-key 式右下角提示面板
- 不引入系统级全局快捷键
- 不做跨平台快捷键兼容逻辑，不为 `Ctrl` / `Command` 做双写分支
- 不做复杂的快捷键分组搜索、导入导出或多套 profile

## Decisions

### 决策 1：引入应用级快捷键注册中心，而不是在各组件里分散监听 `keydown`

**选择**：在应用根部新增快捷键状态与动作派发中心，统一管理：

- 动作 ID 与默认快捷键的映射
- 用户自定义快捷键持久化值
- 当前动作处理函数的注册与注销
- 全局键盘事件监听与命中分发

首批动作 ID 固定为：

- `toggle-file-tree`
- `toggle-terminal-sidebar`
- `create-workspace`

**理由**：这 3 个动作分别落在 `App` 和 `TerminalPanel` 两个层级，继续分散写 `window.addEventListener('keydown')` 会导致快捷键定义、冲突处理和设置同步逻辑四处分散。统一中心后，后续扩展更多动作时只需要新增动作声明和处理函数。

**替代方案**：继续在 `App`、`TerminalPanel`、设置面板内各自监听键盘事件。这样会快速制造重复匹配逻辑，也不利于后续 which-key 能力复用。

### 决策 2：设置面板使用应用内模态层，而不是新开独立窗口

**选择**：设置面板作为渲染进程内的覆盖层组件挂在 `App` 根部，通过 `Command + ,` 打开，通过关闭按钮或遮罩关闭。

**理由**：用户给出的目标形态是应用内设置界面，不是系统独立偏好窗口。复用现有 React 结构能直接访问主题、分栏状态和快捷键配置上下文，复杂度最低。

**替代方案**：在 Electron 主进程再创建一个设置窗口。这样会引入额外窗口生命周期、IPC 同步和样式重复，不符合本次最小实现目标。

### 决策 3：`Command + ,` 固定为设置面板入口，不纳入本次可配置列表

**选择**：本次仅允许配置以下 3 个动作：

- 文件树展示/收起
- terminal tab 侧边栏展示/收起
- 新增 workspace

设置面板入口 `Command + ,` 保持固定。

**理由**：用户明确要求本次“设置面板支持设置”上述 3 个快捷键，没有要求把设置入口本身也做成可编辑项。把入口固定可以降低递归配置复杂度，也更符合 macOS 应用对偏好面板入口的预期。

**替代方案**：将设置入口也做成可配置项。这样会引入“设置面板打开方式丢失”这类恢复问题，不适合作为第一版。

### 决策 4：快捷键配置采用“草稿编辑 + 保存提交”模型，并在保存时做冲突校验

**选择**：设置面板中的快捷键编辑不即时写入运行态，而是先写入草稿表单；用户点击保存后统一校验并提交到持久化存储。校验规则：

- 不允许空快捷键
- 不允许两个动作绑定为同一组合键
- 保存成功后运行态立即刷新为最新绑定

**理由**：用户给出的参考界面包含明确的关闭/保存操作，说明设置面板更适合批量编辑后统一提交。这样也能避免用户录入一半时就污染当前快捷键状态。

**替代方案**：每次录入立即生效。实现更简单，但会让录入过程中的半成品值立刻接管应用，不利于撤销和冲突处理。

### 决策 5：terminal 相关动作由 `TerminalPanel` 注册处理函数，而不是通过 props 级联命令

**选择**：`App` 负责文件树显隐和设置面板开关，`TerminalPanel` 在挂载时向快捷键中心注册：

- `toggle-terminal-sidebar`
- `create-workspace`

对应处理函数。

**理由**：terminal 的内部状态已经封装在 `TerminalPanel` 中，包括 workspace 列表、侧边栏收起状态和创建逻辑。直接在组件内部注册动作，比从 `App` 层一路透传 ref 或命令回调更贴近现有边界。

**替代方案**：把 terminal 的命令提升到 `App`，再通过 props/ref 驱动 `TerminalPanel`。这样会扩大 `App` 的职责范围，也会让 terminal 状态边界变模糊。

### 决策 6：快捷键表示采用规范化字符串，按 macOS 规则录入和匹配

**选择**：在持久化层和运行态都使用规范化组合键字符串，例如：

- `Meta+S`
- `Meta+B`
- `Meta+T`

录入组件只接受本次范围内需要的修饰键组合，匹配逻辑按 macOS `metaKey` 规则执行，不为 `Ctrl` 提供兼容写法。

**理由**：仓库约束已经明确“不写兼容性代码，除非用户主动要求”。既然用户给出的默认组合全部是 `Command`，第一版就应直接采用 macOS 语义，避免额外分支。

**替代方案**：统一抽象成跨平台快捷键层，同时兼容 `Ctrl` / `Meta`。这会把实现复杂度提前拉高，不符合当前范围。

## Risks / Trade-offs

- **[`Command + S` 会覆盖常见保存心智]** → 本次以用户明确要求为准，在设置面板中清晰展示默认绑定，后续若有冲突反馈再调整默认值
- **[快捷键监听与文本输入冲突]** → 当焦点位于快捷键录入框或普通文本输入控件内时，全局动作分发跳过，避免误触
- **[动作处理函数可能晚于快捷键中心初始化]** → 为每个动作提供注册检查，只有已注册动作才能响应；未注册时忽略且不报错
- **[设置面板持续扩展后结构膨胀]** → 首版按“面板容器 + 快捷键区块”组织，保留未来增加左侧分类导航的空间，但本次不提前实现完整设置体系

## Migration Plan

1. 在应用根部引入快捷键配置模型、默认值和持久化读取
2. 实现设置面板壳层，并接入 `Command + ,` 的打开/关闭
3. 将文件树显隐动作接入快捷键中心
4. 将 `TerminalPanel` 的侧边栏显隐和新增 workspace 动作接入快捷键中心
5. 补充设置面板中的快捷键编辑、冲突校验与保存逻辑
6. 若实现过程中出现严重交互回归，可暂时保留设置面板 UI，但关闭用户自定义保存，仅使用默认快捷键继续推进
