## Context

当前终端渲染链路已经支持 WebGL、Canvas 和 DOM 三层策略，但默认偏好仍是“优先尝试 WebGL renderer”。这一路径在现有应用环境下存在页面乱码的已知问题，导致首次使用终端时就可能遇到显示异常。与此同时，Canvas 渲染链路已经具备可用性，因此本次设计的重点不是新增渲染能力，而是调整默认策略与设置说明，让系统优先走稳定路径。

该变更同时跨越终端初始化逻辑和设置面板默认值展示逻辑，属于一个小范围的跨模块行为调整，需要明确默认值来源、存量偏好处理方式以及设置文案边界。

## Goals / Non-Goals

**Goals:**

- 在用户未保存 renderer 偏好时，终端默认采用 Canvas 渲染。
- 保留用户显式启用 WebGL 的能力，并继续维持 WebGL → Canvas → DOM 的失败回退链路。
- 在设置面板中清楚标注 WebGL 存在页面乱码的已知 bug，降低误开启成本。
- 将变更限制在默认行为和设置说明层，不引入额外 renderer 分支或兼容性逻辑。

**Non-Goals:**

- 不修复 WebGL 本身的乱码问题。
- 不改变 Canvas、DOM renderer 的现有实现细节。
- 不强制覆盖用户已经保存的 renderer 偏好。
- 不新增独立的“实验功能”系统或更复杂的灰度开关。

## Decisions

### 1. 默认 renderer 偏好改为关闭 WebGL

当本地不存在已保存的 terminal renderer 偏好时，系统将“优先尝试 WebGL renderer”视为关闭状态。这样新建或重新初始化终端实例时将直接尝试 Canvas，Canvas 不可用时再回退到 DOM。

选择这个方案，是因为用户当前反馈的是默认 WebGL 路径存在稳定性问题；问题不在于用户是否可以手动开启，而在于默认策略把用户带入了已知有 bug 的路径。将默认值改为关闭，可以立即降低首次使用风险，同时保留调试和手动开启能力。

备选方案：

- 保持默认启用 WebGL，仅增加设置说明。未采用，因为这无法解决首次启动即命中乱码的问题。
- 彻底移除 WebGL 选项。未采用，因为用户只要求默认不使用 WebGL，没有要求删除能力，而且保留选项有利于后续验证问题是否已修复。

### 2. 存量已保存偏好不做迁移覆盖

本次变更只影响“无已保存值”时的默认解析逻辑，不主动重写 localStorage 中已有的 renderer 偏好。已经手动开启或关闭过 WebGL 的用户继续沿用其现有设置。

选择这个方案，是为了把变更控制在“默认值修正”而不是“强制迁移”，避免悄悄覆盖用户决策，也避免引入额外的一次性迁移逻辑。

备选方案：

- 启动时统一把历史偏好重置为关闭。未采用，因为这会改变已显式选择的用户设置，超出本次需求。

### 3. 设置面板增加明确的风险备注

设置面板中的终端 renderer 配置区除了布尔开关本身，还需要展示一段静态说明，明确指出 WebGL 存在页面乱码的已知 bug。说明文案应直接服务于用户判断，不使用模糊表达。

选择这个方案，是因为单靠开关标题不足以解释为什么默认关闭；把风险说明放在配置项附近，用户在主动开启前就能看到后果。

备选方案：

- 仅在用户开启 WebGL 后弹出提示。未采用，因为提示出现得太晚，且会增加交互打断。
- 将问题说明写入独立帮助文档。未采用，因为可见性太低，不能覆盖设置操作当下的决策场景。

## Risks / Trade-offs

- [部分依赖 WebGL 性能的用户会失去默认性能路径] → 保留设置开关，允许用户手动重新启用 WebGL。
- [Canvas 在个别环境下也可能不可用] → 继续维持 Canvas → DOM 的现有回退链路，避免终端不可用。
- [设置备注过于弱化可能无法起到告知作用] → 文案中直接写明“WebGL 有 bug（页面乱码）”，避免抽象措辞。
- [默认值调整与已保存值并存，可能让不同用户看到不同初始状态] → 在实现中把“默认值”和“已保存值”来源区分清楚，确保行为可解释。

## Migration Plan

1. 调整 renderer 偏好读取逻辑，使“未配置”默认解析为关闭 WebGL。
2. 更新设置面板默认展示状态与帮助文案。
3. 保持已保存偏好不变，避免对现有用户做强制迁移。
4. 通过手动验证确认三条路径：默认 Canvas、显式启用 WebGL、Canvas 不可用时回退 DOM。

## Open Questions

- 无。本次范围内的行为边界已经明确：默认值改为 Canvas，WebGL 保留为用户显式开启选项，并在设置中标注已知乱码问题。
