## Context

当前快捷键系统以 [src/ShortcutContext.tsx](/Users/zhoushitie/My/AItem.browser-keymap/src/ShortcutContext.tsx) 为中心，通过渲染进程 `window` 上的 `keydown` 监听将单一快捷键映射分发给注册动作。它适合处理 terminal、文件树、设置面板这类同一渲染上下文内的动作，但对内置浏览器存在两个明显限制：

1. 地址栏是受控 `<input>`，现有 `isEditableTarget()` 会直接跳过输入类元素，因此 `Cmd+L` 在地址栏获焦时不会触发浏览器开关。
2. 网页内容运行在 `<webview>` 的独立 `webContents` 中，很多组合键不会冒泡回主渲染进程，导致仅依赖 `window.keydown` 无法在网页获焦时稳定接管浏览器快捷键。

同时，terminal 已经占用了 `Cmd+T`、`Cmd+W`、`Cmd+Shift+[`、`Cmd+Shift+]`、`Cmd+1..9` 等默认绑定。用户希望浏览器打开时这些组合键表现得更像真实浏览器，而浏览器关闭后仍保留现有 terminal 行为。这是一个跨越 `ShortcutContext`、`App`、`BrowserPanel`、主进程 webview 生命周期和 preload IPC 的横切变更。

## Goals / Non-Goals

**Goals:**
- 让 `Cmd+L` 成为浏览器面板的保留开关键，在浏览器打开或关闭、地址栏获焦或网页内容获焦时都稳定工作。
- 在浏览器面板打开时，为 `Cmd+T`、`Cmd+W`、`Cmd+Shift+[`、`Cmd+Shift+]`、`Cmd+1..9`、`Cmd+R`、`Cmd+[`、`Cmd+]` 提供浏览器语义。
- 在浏览器面板关闭时，保持现有 terminal / workspace 快捷键行为不变。
- 保持浏览器标签状态仍由 `BrowserPanel` 持有，避免把浏览器 tab 状态提升到全局。
- 修正网页新窗口被转为新标签时，浏览器面板未显示也会自动打开的问题。

**Non-Goals:**
- 不重做现有快捷键设置页，不将浏览器上下文快捷键纳入用户自定义配置。
- 不改变 terminal 默认快捷键绑定，也不提供兼容模式切换。
- 不引入菜单栏 accelerator 或系统级 `globalShortcut`。
- 不在本次变更中扩展书签、历史管理、下载管理等浏览器能力。

## Decisions

### 决策一：将浏览器快捷键定义为“固定上下文快捷键”，不进入当前用户绑定表

**选择**：保留现有 `ShortcutContext` 的用户绑定表只服务工作台级动作；浏览器相关冲突组合键作为固定的浏览器上下文快捷键，仅在浏览器面板打开时生效。

**原因**：
- 当前校验逻辑要求一个快捷键只能绑定一个动作；若把浏览器与 terminal 的 `Cmd+T` / `Cmd+W` 等都放进同一绑定表，会直接引入重复冲突。
- 用户诉求是“浏览器打开时像真实浏览器”，而不是“新增一套可配置的浏览器动作中心”。固定上下文语义更符合产品目标，也能显著控制范围。

**备选方案**：
- 让设置页支持“按上下文重复绑定”。这需要重写绑定模型、校验规则、UI 展示和冲突提示，范围过大，不采用。

### 决策二：将 `Cmd+L` 视为保留开关键，绕过可编辑元素屏蔽

**选择**：`Cmd+L` 不再完全依赖现有“先判断 editable，再决定是否处理”的全局分发流程，而是提升为浏览器面板保留开关动作。

**原因**：
- 地址栏输入框本身就是浏览器 chrome 的一部分，把 `Cmd+L` 交给输入框会让浏览器开关键失效，违背明确需求。
- 用户已经明确要求 `Cmd+L` 无论浏览器当前处于开或关都能切换，因此这里不能沿用真实浏览器的“聚焦地址栏”语义。

**备选方案**：
- 浏览器打开时将 `Cmd+L` 改成聚焦地址栏，浏览器关闭时再作为打开动作。该方案更像 Chrome，但与当前产品诉求冲突，不采用。

### 决策三：浏览器快捷键分两条输入链路处理，最终汇总到 BrowserPanel

**选择**：
- 渲染进程负责处理浏览器 chrome 区域可见的按键：标题区、标签栏、地址栏、空状态页。
- 主进程在 `web-contents-created` 钩子中为浏览器 `webview` 注册 `before-input-event` 监听，拦截网页内容获焦时的浏览器快捷键，再通过 IPC 发回渲染进程。
- `BrowserPanel` 作为浏览器标签和导航状态的唯一拥有者，对两条链路来的命令执行统一动作。

**原因**：
- `window.keydown` 能覆盖地址栏与浏览器面板自身控件，但不能稳定覆盖网页内容。
- `before-input-event` 是 Electron 中处理 `webContents` 级快捷键的稳定入口，适合拦截 `Cmd+L`、`Cmd+T`、`Cmd+W`、`Cmd+R` 等浏览器组合键。
- 把动作收口到 `BrowserPanel`，可以避免在主进程复制 tab 状态逻辑。

**备选方案**：
- 只在渲染进程监听 `keydown`。网页内容获焦时不可靠，不采用。
- 把所有浏览器 tab 状态迁移到主进程统一控制。实现复杂度更高，且当前没有跨窗口共享需求，不采用。

### 决策四：采用“浏览器打开时优先消费冲突快捷键，关闭时完全释放”的上下文策略

**选择**：当浏览器面板打开时，浏览器快捷键优先于 terminal 同名快捷键；浏览器面板关闭时，这批快捷键不再由浏览器消费，原工作台逻辑继续生效。

**原因**：
- 这是最符合用户心智的状态切换模型：进入浏览器就像进入一个浏览器上下文，离开后回到工作台上下文。
- 能在不改动 terminal 默认绑定的前提下解决 `Cmd+T` / `Cmd+W` 等冲突。

**备选方案**：
- 永远让浏览器优先。会破坏现有 terminal 快捷键，不采用。
- 永远保留 terminal 优先。无法满足浏览器行为诉求，不采用。

### 决策五：浏览器新窗口转新标签时同时负责打开面板

**选择**：保留现有 `setWindowOpenHandler` → IPC → `addTab(url)` 结构，但补上“若浏览器当前未显示，则同步打开面板并激活新标签”这一职责。

**原因**：
- 当前 spec 已要求此行为，但现状只会加标签，不会展开面板。
- 用户从网页触发 `target="_blank"` 时，必须立即看到结果，否则会误判为没有响应。

**备选方案**：
- 仅后台创建标签，不自动展开面板。反馈弱且不符合现有 spec，不采用。

## Risks / Trade-offs

- **浏览器快捷键链路分散** → 通过统一的浏览器命令枚举和单一 `BrowserPanel` 命令入口收口，避免渲染/主进程两边各自维护一套语义。
- **`Cmd+L` 与真实浏览器“聚焦地址栏”习惯不一致** → 明确将其定义为本产品的浏览器开关键，并仅在 spec 中承诺切换行为，不混入聚焦地址栏语义。
- **网页内容快捷键拦截可能误伤站点自身组合键** → 仅拦截少量明确保留的浏览器组合键，其余按键保持透传给网页。
- **浏览器快捷键未进入设置页，行为对用户不可见** → 通过 spec 和后续 UI 文案/tooltip 补充说明；本次不扩展设置页，避免范围失控。
- **webview 生命周期与 IPC 桥接不当可能造成重复监听** → 在设计上要求监听绑定与销毁跟随 webContents 生命周期，并以 tab/webview 实例为粒度清理。
