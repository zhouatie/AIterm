## Context

当前 `ContextMenu` 组件使用固定定位，并通过 `x + width > window.innerWidth` 的方式只对窗口右边界做避让。`FileTree` 在触发右键菜单时只传入鼠标坐标和节点路径，没有把文件树面板自身的几何边界传给菜单。

这在全窗口级菜单里是合理的，但文件树右键菜单的交互语义并不是“允许覆盖任意相邻面板”，而是“作为文件树面板内部操作菜单出现”。因此现状会在左栏较窄时把菜单绘制到右侧面板区域，造成视觉和操作上的错位。

## Goals / Non-Goals

**Goals:**
- 让文件树右键菜单始终完整显示在文件树面板可视范围内。
- 保持现有菜单项顺序、动作、关闭时机和视觉样式不变。
- 将变更范围限制在文件树菜单的定位输入和定位计算上，避免引入新的菜单系统抽象。

**Non-Goals:**
- 不改成 Electron 原生上下文菜单。
- 不重做 `ContextMenu` 的整体视觉样式或交互模型。
- 不顺带修改 terminal 侧边栏等其他位置对 `ContextMenu` 的使用方式。

## Decisions

### 决策 1：为 `ContextMenu` 增加可选的宿主边界参数

**选择**：在 `ContextMenu` 上增加一个可选 `bounds`（或等价命名）参数，用于描述菜单应尽量停留的可视矩形；未传入时继续按窗口视口处理。

**理由**：问题出在定位边界选错，不在菜单项本身。给菜单增加可选边界参数，可以把“文件树约束在文件树内”的需求显式建模，同时不破坏其他调用方的当前行为。

**替代方案**：仅在 `FileTree` 内部预先改写 `x`/`y`，把坐标硬编码为一个已经避让后的值。这样改动最小，但会把菜单尺寸与边界逻辑散落到调用方，不利于复用，也让后续菜单宽度变化更难维护。

### 决策 2：文件树使用自身容器矩形作为优先边界

**选择**：`FileTree` 右键时从根容器或滚动容器读取 `getBoundingClientRect()`，把该矩形传给 `ContextMenu`；菜单横向定位优先依据这个矩形的 `left/right` 做避让。

**理由**：用户感知到的“菜单不该越界”的边界是文件树面板本身，而不是整个窗口。用文件树容器矩形作为边界，能直接覆盖当前缺陷场景，也不需要引入 portal 或额外层级。

**替代方案**：把菜单挂载到文件树滚动容器内并依赖 CSS `overflow`。这会让菜单跟随滚动容器裁切和滚动，反而更容易出现滚动偏移、层级和遮挡问题；现有 `position: fixed` 更适合保留。

### 决策 3：只收紧文件树菜单的可视边界，不扩大为全局规则变更

**选择**：`ContextMenu` 仅支持“可选 bounds”；文件树传入 bounds，其他使用方保持现状。

**理由**：当前能确认有问题的是文件树场景。直接把所有上下文菜单都改成受最近容器约束，会改变 terminal panel 等现有行为，属于超出本次问题范围的设计风险。

**替代方案**：强制所有 `ContextMenu` 必须传边界。这样一致性更强，但需要同时清点所有调用点并重新定义它们的宿主边界，不符合本次小修复的目标。

## Risks / Trade-offs

- **[风险] 文件树容器边界读取节点选错，导致菜单仍然对不齐** → 缓解：使用真正代表文件树可视区域的外层容器，而不是虚拟列表内部占位层或单行节点。
- **[风险] 菜单宽度未来变化后，调用方预估失真** → 缓解：宽度和避让计算仍集中在 `ContextMenu` 内部，调用方只传边界，不自己算偏移。
- **[取舍] 其他面板的菜单暂不统一到“宿主边界”语义** → 这是刻意范围控制，先修复已确认缺陷，再按需抽象全局规则。
