## Context

当前应用已经具备较完整的 terminal workspace / tab 能力，终端导航、文件树、标题栏、主题切换和分栏拖拽都已成型，但这些模块的视觉语言来自不同阶段的独立迭代。结果是界面虽然功能齐全，却存在明显的“工具拼装感”：标题栏像工具栏，terminal 侧边栏像普通树形列表，分隔线和阴影表达偏硬，终端内容区与外层窗口 chrome 之间缺少统一关系。

这次变更是一次跨 `TerminalPanel`、`App`、`SplitLayout`、`index.css` 和终端容器样式的视觉系统整理。目标不是重做信息架构，也不是增加新功能，而是在保持现有 workspace / terminal tab 交互模型不变的前提下，让界面更接近 macOS 桌面应用常见的克制、细腻、层次清楚的观感。

约束如下：
- 不改动 workspace / tab 的功能语义、快捷键语义或 PTY 生命周期。
- 不引入新的样式库，继续沿用现有 React 内联样式 + 全局 CSS 变量方案。
- 不写兼容性代码，直接以新的主题 token 和视觉结构替换当前表现。
- 当前没有 terminal tab 对应的 Figma 节点可直接消费，因此设计需要基于现有代码结构与桌面应用约定收敛。

## Goals / Non-Goals

**Goals:**
- 为标题栏、主分栏、terminal 侧边导航和终端内容区建立统一的窗口级视觉语言。
- 提升 workspace 与 terminal tab 的层级表达，使一级容器与二级会话在密度、字重、背景和交互反馈上有清晰区分。
- 用更柔和的表面层次、描边、阴影和强调色替换当前偏硬的 hover / selected 表达，并在浅色与深色模式中保持一致。
- 保持 terminal 内容区作为主要工作区域的纯净感，减少不必要的浮层感和高饱和提示。
- 让新的视觉方案可以通过现有主题系统与组件结构落地，不新增额外框架成本。

**Non-Goals:**
- 不修改 terminal、workspace、文件树或设置面板的功能范围。
- 不新增窗口拖拽排序、动画编排系统、毛玻璃原生 API 或自定义主题编辑能力。
- 不引入新的图标库、设计令牌构建工具或 CSS-in-JS 方案。
- 不要求一次性重构全应用所有组件；本次只覆盖与 terminal workbench 主体验直接相关的区域。

## Decisions

### 决策 1：以主题 token 扩展为先，而不是逐组件打补丁

**选择**：先扩展全局主题语义变量，再让 `App.tsx`、`SplitLayout.tsx`、`TerminalPanel.tsx` 和 `TerminalInstance.css` 消费这些 token。

**理由**：当前界面的割裂感，本质上来自不同区域使用了过于粗糙的背景、边框、hover、selected 和阴影语义。若直接在单个组件里局部调颜色，很容易继续制造新的漂移。先补齐窗口 chrome、表面层级、柔和选中态、细描边、分隔层和注意力提示等 token，才能让多个区域共享同一套视觉规则。

**替代方案**：只在 `TerminalPanel.tsx` 中局部调样式。实现更快，但标题栏、分栏和终端画布不会同步提升，最终仍是局部精致、整体割裂。

### 决策 2：保持现有结构模型，只重塑视觉层次

**选择**：保留当前的标题栏结构、左右分栏结构、workspace / session 树结构和 collapse 机制，不修改交互信息架构，只调整视觉密度、层级和状态表达。

**理由**：现有 OpenSpec 已明确规定 terminal tab 采用左侧双层导航结构，且代码中这套模型已经稳定。用户当前反馈的是“不够优雅”，而不是“结构错误”。在探索阶段直接重组结构会把视觉问题和交互问题混在一起，增加风险。

**替代方案**：重做 terminal 导航布局，例如重新引入横向 tabs 或把 workspace 改成卡片式块。这样会扩大变更范围，也偏离已有 spec。

### 决策 3：将 terminal 侧边栏视为统一导航表面，而不是一组零散行项

**选择**：把 terminal 侧边栏设计成一个连续的导航容器，在这个容器内部通过 workspace 行、session 行、hover、active、attention 和行内操作按钮表达层次，而不是让每一行都像独立按钮。

**理由**：macOS 风格的精致感通常来自整体容器的安静与局部交互的克制，而不是给每个元素都画出清晰边界。对当前 terminal sidebar 来说，真正该强调的是“容器中的层级关系”，不是“每行自己的块感”。

**替代方案**：继续沿用高对比整行底色 + 圆角按钮 + 明显 hover 底。这样会维持 IDE 风格，难以达到桌面应用的柔和感。

### 决策 4：活跃态使用低对比焦点表达，不再依赖高饱和整行选中底

**选择**：terminal session 的活跃态采用更克制的焦点样式，例如轻微提亮、精细描边、局部强调色或前景字重变化；注意力提示继续独立表达，不与活跃态争抢主色。

**理由**：当前 `selected` 蓝底在功能上清楚，但视觉上过于直接，会让整个 sidebar 看起来像列表控件而不是工作台导航。苹果系应用更常见的是低对比选中 + 准确的层级密度，而不是强饱和大块色。

**替代方案**：保留当前蓝底，只把圆角和阴影做得更柔和。这样只能缓和一点工具感，无法真正改变整体气质。

### 决策 5：标题栏与主分栏共享同一套窗口 chrome 语义

**选择**：将标题栏、主内容区顶部边界、分栏分隔和右侧面板容器视为同一窗口壳层的不同部位，通过统一背景、细描边、分层阴影和控件 hover 规则保持连贯。

**理由**：当前标题栏与下方内容区像两块简单拼接的区域，缺少连续性。只优化 terminal sidebar 而不处理窗口 chrome，会让“苹果风格”停留在局部。窗口观感的一致性是这次变更的关键。

**替代方案**：只改 terminal 区，不动标题栏和分栏。这样用户仍会感知到顶层窗口壳是旧风格。

### 决策 6：终端内容区保持克制，优先服务可读性

**选择**：终端画布本身维持低干扰表现，只在容器边缘、背景层次和与 sidebar 的衔接处做轻量优化，不在终端区域引入装饰性强的背景或多余控件。

**理由**：terminal 是高频、高信息密度区域，真正需要的是清晰和稳定。苹果风格不等于增加效果，而是减少噪音、控制节奏。把视觉处理集中在容器和边界，比给 terminal 本身加重装饰更稳妥。

**替代方案**：给 terminal 区加入明显卡片、厚阴影或大面积材质背景。这样会影响长期使用的专注度，也容易显得做作。

### 决策 7：直接替换旧 token，不保留视觉兼容层

**选择**：新的表面与状态语义直接替换现有 token 引用，不额外保留旧视觉变量或旧分支样式。

**理由**：项目约束已明确不写兼容性代码。这类视觉系统改造如果保留双轨 token，会让代码和语义都迅速膨胀，后续维护成本高。

**替代方案**：同时保留“旧 theme token”和“新 visual token”，再逐步切换。适合大型长期迁移，但对当前仓库和这次范围而言过重。

## Risks / Trade-offs

- **[视觉目标抽象、缺少直接设计稿]** → 先用 spec 固定用户可感知结果，再在实现阶段控制每个区域的改动幅度，避免“凭感觉大改”。
- **[多模块联动导致风格不一致]** → 以 token 为中心推进，先收敛表面/描边/选中/阴影语义，再分组件落地。
- **[过度追求苹果感导致终端可用性下降]** → 终端内容区保持低干扰，优先保证文字对比、焦点识别和空间利用。
- **[TerminalPanel 目前大量使用内联 hover 逻辑，视觉细化后代码会更啰嗦]** → 仅把稳定复用的语义提到 token / 常量层，避免引入新样式框架。
- **[深色模式容易被做成“全黑 + 高蓝光”]** → 在 spec 中要求浅/深主题保持相同的层级逻辑，而不是只换一组深色值。

## Migration Plan

1. 先扩展并重命名需要的主题语义变量，确定窗口 chrome、表面层级、hover、selected、attention、divider 和 shadow 的新规则。
2. 调整 `App.tsx` 与 `SplitLayout.tsx`，让标题栏、主内容区和分栏边界形成统一的窗口结构。
3. 重做 `TerminalPanel.tsx` 的视觉层次，包括 workspace / session 行、按钮显隐、活跃态和收起 / 展开入口。
4. 微调 `TerminalInstance.css` 与相关容器样式，使 terminal 画布与外层工作台自然衔接。
5. 分别在浅色与深色模式下验证整体层级与对比关系，必要时细调 token，但不回退到旧视觉方案。

## Open Questions

无。当前变更聚焦视觉表达优化，功能边界和信息架构已足够明确。
