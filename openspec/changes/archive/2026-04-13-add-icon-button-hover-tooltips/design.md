## Context

当前应用里的 icon-only 操作按钮已经分散在多个模块中：

- `App.tsx` 顶部标题栏包含文件树显隐按钮和主题切换按钮
- `FileTree.tsx` 工具栏包含刷新、展开/收起等按钮
- `TerminalPanel.tsx` 包含新建 workspace、新建 terminal tab、关闭 terminal tab、terminal 侧边栏收起/展开按钮
- `SettingsPanel.tsx` 包含右上角关闭按钮

现状里一部分按钮已经带有 `title`，但文案来源分散、命名不统一，也不会跟随当前快捷键绑定变化。与此同时，`ShortcutContext` 已经集中维护动作 ID、当前绑定值和格式化展示能力，因此这次变更的关键不是“再补几个 title”，而是把 icon-only 按钮提示收敛到一套共享规则上。

本次变更是跨 `App`、文件树、terminal、设置面板的横切改动，但不涉及新依赖、主进程改造或兼容性逻辑。

## Goals / Non-Goals

**Goals:**
- 为应用内现有 icon-only 操作按钮统一提供 hover 提示
- 对映射到应用级快捷键动作的按钮，在提示文案末尾追加当前生效快捷键
- 让 tooltip 文案在用户修改快捷键并保存后自动更新
- 保持当前模块边界，不把 tooltip 文案硬编码规则再复制到每个组件里

**Non-Goals:**
- 不引入自定义浮层 tooltip 组件或新的第三方依赖
- 不扩展到带文字标签的按钮、列表行点击区域或右键菜单项
- 不顺带做整站文案本地化或 tooltip 视觉样式改造
- 不新增快捷键动作，也不改动现有快捷键触发语义

## Decisions

### 决策 1：使用共享 tooltip helper 生成文案，而不是在各组件继续手写 `title`

**选择**：新增一层共享 helper，输入“基础功能说明 + 可选 actionId + 当前 bindings”，输出最终 tooltip 文案；各组件只声明按钮当前语义，不自己拼接快捷键后缀。

**理由**：当前 tooltip 已经分散在 `App.tsx`、`FileTree.tsx`、`TerminalPanel.tsx` 中。继续局部硬编码会让文案命名、括号格式和快捷键展示顺序再次失控，也会在设置改绑后形成陈旧提示。

**替代方案**：保留每个组件自行写 `title`，只有快捷键按钮手工拼接 `formatShortcutForDisplay(bindings[actionId])`。这样短期可用，但会把同一套拼接规则复制到多个文件里，后续继续扩展时容易漏改。

### 决策 2：快捷键后缀直接读取运行时生效绑定，而不是写死默认值

**选择**：tooltip 中展示的快捷键统一读取 `ShortcutContext` 当前 `bindings`，并复用已有 `formatShortcutForDisplay` 结果；如果某个按钮不映射到快捷键动作，则只展示基础功能说明。

**理由**：当前系统已经支持用户修改并保存快捷键。如果 tooltip 仍然写死默认值，设置面板保存后，按钮 hover 提示会立刻与真实行为不一致，这是本次变更必须避免的问题。

**替代方案**：tooltip 一律展示默认快捷键或完全不展示快捷键。前者会在改绑后失真，后者则无法满足“功能说明后面加上快捷键”的明确需求。

### 决策 3：继续使用原生 `title` 提示，不引入自定义 Tooltip 组件

**选择**：本次继续复用浏览器原生 `title` 作为 hover 提示载体，只调整文案生成方式和覆盖范围。

**理由**：你的需求是“给所有 icon 按钮加上 hover 提示功能”，不是重做 tooltip UI。当前代码里已经广泛使用 `title`，沿用这条路径成本最低，也不会引入额外浮层定位、层级和主题样式问题。

**替代方案**：实现一个统一的 React Tooltip 组件。这样视觉可控性更强，但范围会迅速扩展到样式、交互延时、portal 和可访问性细节，超出本次目标。

### 决策 4：按钮 tooltip 基础文案按当前 UI 状态生成，但快捷键后缀保持动作级稳定

**选择**：对切换类按钮，基础文案使用当前状态语义，例如“收起文件树”/“展开文件树”、“收起 Terminal 侧边栏”/“展开 Terminal 侧边栏”；若它们对应同一个快捷键动作，则后缀继续显示同一个当前绑定值。

**理由**：用户 hover 时首先需要知道“此刻点击会发生什么”，而不是抽象动作名。状态切换类按钮如果只显示“文件树展示/收起”虽然不算错误，但可操作性弱于直接描述当前点击结果。

**替代方案**：直接复用 `SHORTCUT_ACTIONS.title` 作为 tooltip 主文案。这样实现更简单，但会损失状态信息，尤其在显隐切换按钮上不够直接。

### 决策 5：本次纳入范围限定为现有 icon-only 操作按钮

**选择**：纳入范围的对象是“点击目标本身只由图标表达操作语义”的按钮，包括标题栏按钮、文件树工具栏 icon 按钮、terminal 侧边栏 icon 按钮和设置面板关闭按钮；不包含 `spec` 这类文字按钮、workspace/session 行容器、设置页带文案的保存/关闭按钮。

**理由**：用户明确要求“所有 icon 按钮”。这类按钮最依赖 hover 提示补足可发现性，而文字按钮本身已经有直接标签，继续纳入会扩大范围但收益有限。

**替代方案**：把所有可点击元素都纳入 tooltip 规范。这样会把列表行、右键菜单、表单操作一并卷入，边界过大且不符合这次输入。

## Risks / Trade-offs

- **[仍然使用原生 `title`，交互形态较基础]** → 本次只解决信息缺失与快捷键失真问题，先不扩大到自定义 tooltip 组件
- **[不同模块当前文案语言风格不完全一致]** → 本次优先统一“是否有 tooltip”和“快捷键后缀规则”，不顺带做整站文案翻译
- **[部分按钮只在 hover 态出现，例如 workspace 的新增 tab 按钮]** → 仍然为其补齐 tooltip，保证鼠标停留到按钮本身时能看到说明
- **[后续新增 icon 按钮可能再次漏接入]** → 通过共享 helper 和 spec 约束降低漏配概率，后续新增按钮时按同一规则接入

## Migration Plan

1. 在共享层补充 tooltip 文案生成 helper，并约定快捷键后缀格式
2. 盘点现有 icon-only 按钮，为每个按钮补充基础功能说明和可选 actionId
3. 将 `App.tsx`、`FileTree.tsx`、`TerminalPanel.tsx`、`SettingsPanel.tsx` 中相关按钮接入统一 helper
4. 验证默认绑定下的 tooltip 文案，以及在设置面板改绑并保存后的实时更新效果
